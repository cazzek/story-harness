# シナリオのレビュー

`docs/シナリオ制作ハーネス.md` と `シナリオ管理/正本と知識.md` に従う。同じ作業領域の4ファイル（文脈、構成案、本文案、状態抽出）を読む。単独で実行でき、他のエージェントの起動は必須ではない。

1. 文脈の全参照元のSHA-256と未作成状態を照合する。既存の差分を保護し、入力に変更があれば先行工程を更新する。
2. 依頼の狙い、対象外、合格条件と、構成案、本文案、状態抽出を突き合わせる。
3. 正本の決定状態、人物像、本文の調子、情報の4層の分離を確認する。案に影響する矛盾や未決の判断を隠さない。
4. 対象の範囲ごとに入口、出口、条件、選択肢、合流、知識を追う。まだ到達していない経路で得た情報や、退場した人物の無条件の再登場を見落とさない。
5. 適用対応表に沿って、識別子の一意性、参照と遷移の宛先、戻り先、フラグの定義と利用を確認する。構造変更では一時コピーへ仮適用し、利用可能な検証手段（文法チェック、lint、リンク確認など）で確認する。本編は変更しない。
6. 抽出差分の本文根拠と条件、資料同期、制作量を確認する。必要な環境が使えない場合、実施済みとは書かない。手動確認が必要な項目は、必要性と実施状況を示す。
7. 構成案の「場面で起こす変化」と本文を照合し、人物の目的、行動の理由、会話の反応、選択の動機と代償、反復と余韻を点検する。整合性と作劇を別々に判定し、構成案の合格条件に関わる問題を直す。レビュアーの好みを必須条件にしない。
8. 必要な場合は、ハーネスの「作劇と読み味の確認」に従い、先行本文と対象本文だけで読者観測を行う。新しい読み手を使う場合、設定集、構成案、作者の意図と狙い、先行レビューを渡さない。既にそれらを読んだ主体が独立観測を実施したとは書かない。観測の入力、実施者、限界、採否を記録する。
9. `シナリオ管理/書式/レビュー.md` を使い、4ファイルの実測SHA-256、検証結果、反映対象の全ファイルと正確な差分を、同名の作業ファイルへ記録する。読者観測後に本文を変えた場合は、再抽出と再レビューを行い、古い観測結果は変更前の版にだけ対応させる。

判定は `PASS` または `BLOCKED`。必須検証の失敗や未実施、設定矛盾、知識漏洩、構造破壊、ハッシュ不一致、根拠のない抽出、必須のユーザー判断が残ればBLOCKEDとする。依頼範囲内で直せる問題は修正し、再抽出と再レビューを行う。条件付きPASSにはしない。

レビュー済みの案と検証結果を提示する。PASSでも本編は変更しない。対象案への明示承認がある場合だけ `story-commit` へ進む。
