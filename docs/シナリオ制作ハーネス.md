# シナリオ制作ハーネス

## 目的と範囲

StoryHarnessは、AIエージェントと人間が長編シナリオを共同で書くための工程管理の仕組みです。狙いは、文章の上手さではなく整合性の担保にあります。

- 正本（確定した本文と設定）と、制作中の案を分離する
- 誰が何を知っているか（作者、人物、読者）を混ぜない
- 採用は必ずレビューと作者の明示承認を経る

1回の作業は、章、または章内の節（場面）に絞ります。

## 使用方法

「第3章を書きたい」「第1章のこの場面を伸ばしたい」のように依頼すれば、AIエージェントは `AGENTS.md` を入口にハーネスを使います。工程名（`$story-context` など）で直接指定しても構いません。

| 工程 | 作るもの | 本編の変更 |
|---|---|---|
| 文脈（story-context） | 文脈.md | なし |
| 構成（story-plan） | 構成案.md | なし |
| 執筆（story-write） | 本文案.md | なし |
| 状態抽出（story-extract） | 状態抽出.md | なし |
| レビュー（story-review） | レビュー.md | なし |
| 採用反映（story-commit） | 反映記録.md、承認された差分 | レビューPASSと対象案への明示承認後 |

通常は本命1案をレビューまで作って提示します。レビューPASSだけでは本編へ反映しません。ハーネスの導入依頼や、単なる感想は、物語案の採用承認ではありません。

## 情報の4層

文脈、構成、抽出では、次の4層を分けて扱います。

| 層 | 扱うこと | 注意 |
|---|---|---|
| 作者意図 | どんな読書体験にするか、文体、制約 | 推測で増やさない |
| 作中の事実 | 実際に起きたこと、人物がしたこと | 人物の決意や主張を事実と混ぜない |
| 人物の知識と自覚 | 各人物が知る、信じる、疑う、認めていないこと | 時点を付けて記録する |
| 読者への開示 | 本文で読者が読めること | 正本を読んだAIの知識と混ぜない |

資料の状態（確定、未決、候補）をAIの判断で勝手に昇格させません。外部からの改稿コメントは意図の参考であり、正本ではありません。

## 作劇と読み味の確認

構成では、対象の入口と出口で「人物の自覚、関係、行動の基準がどう変わるか」を決めます。その作品に繰り返しの進行パターンがある場合は、それをなぞるだけにならないよう、今回新しく進む点を一つ明示します。

レビューは整合性と作劇を分けて判定します。整合性（時系列、段階、知識）が通っても、人物の迷いや葛藤が形だけ、感覚の描写が同じ語の繰り返し、場面の終わりに次への引きがない、といった読み味の問題は修正対象です。

読者視点の確認を行う場合は、先行本文と対象本文だけを読み手に渡し、正本や構成案、作者の狙いは渡しません。AIによる読者確認は人間の感想の代わりではなく、採否を自動で決めるものでもありません。

## 配置

- 運用の入口: `AGENTS.md`
- 正本の扱い: `シナリオ管理/正本と知識.md`
- 章と場面の入口: `シナリオ管理/場面索引.md`
- 状態と伏線: `シナリオ管理/状態台帳.md`
- 外部改稿の記録: `シナリオ管理/改稿の履歴.md`
- 本文: 作品の本文フォルダ（例: `脚本/`）
- 書式: `シナリオ管理/書式/`
- 制作中の案: `シナリオ管理/作業/<対象>/<日付と目的>/`
- 採用履歴: `シナリオ管理/採用履歴.jsonl`
- 工程のスキル: `.agents/skills/story-*/SKILL.md`

同名の過去案は上書きしません。書式の山括弧部分は作成時に埋め、不要な欄は「該当なし」と理由を書きます。

## 参照と検証

対象と、その前後、関係する正本だけを読みます。文脈には、読んだファイルのパス、用途、読んだ範囲、SHA-256を記録します。各工程の開始時と、反映の直前に照合し、変わっていれば影響を確認して先行工程からやり直します。Git管理下であれば、反映後に差分確認（`git diff --check` など）で対象外の変更がないことを確かめます。

本文は場面単位で識別子を付けて扱います（例: `第1章-節3`）。識別子は場面索引に合わせます。

## 採用履歴の形式

`シナリオ管理/採用履歴.jsonl` には、採用のたびに次の形式で1行を追記します。過去行の変更、削除、並べ替えはしません。

```json
{"schema_version":1,"event_id":"一意な採用ID","recorded_at":"日時","type":"scene.commit","scene_id":"場面名","proposal_id":"日付と目的","summary":"承認された変更","source_files":[],"deltas":{"world_state":[],"character_knowledge":[],"reader_knowledge":[],"relationships":[],"foreshadowing":[]}}
```

`source_files` は実際の変更先、`deltas` は採用した差分だけを、条件と本文根拠付きで記録します。

## 軽い作業の扱い

設定への質問やハーネス自体の保守では、関係資料の参照だけで構いません。意味、口調、間を変えない誤字修正だけなら工程を省略できます。その場合も、対象、変更前後、承認を確認し、反映記録と採用履歴は残します。

## 分岐を足す場合の拡張

分岐、選択肢、フラグを持つ作品では、文脈と状態抽出に「経路条件」の欄を追加し、経路ごとに人物の知識と読者（プレイヤー）への開示を分けます。別の経路や周回で得た知識を合算しないでください。物語上のフラグと、システム側の解放履歴（既読、達成率など）は分けて記録します。
